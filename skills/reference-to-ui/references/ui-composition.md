# 요소를 덜고 행동을 구분하는 UI 구성

UI 설계·구현 전에 읽는다. 사용자가 Todo 테스트 결과에서 직접 지적한 실패를 반영한 기본 기준이다. 단어만 바꾸거나 숫자를 토큰에 넣는 것으로 통과하지 않는다. 실제 화면에서 정보의 필요성과 행동의 구분을 확인한다.

## 로고와 아이콘

요청하거나 제공한 브랜드 자산이 없으면 로고·심벌·워드마크·슬로건을 임의로 만들지 않는다(RUI-08). 기존 아이콘을 골랐어도 제품명 옆에 장식 마크로 붙이면 같은 문제다. 일반 화면 제목만으로 과제를 식별할 수 있으면 충분하다. ‘제품 식별’이라는 사후 설명은 로고 제작 요구의 근거가 아니다.

기능 아이콘은 행동의 의미를 빠르게 이해하는 데 필요할 때 사용한다(RUI-12). 프로젝트에 있는 검증된 아이콘 세트를 우선하고, 없으면 출처가 명확한 한 세트의 적절한 아이콘을 사용한다. 편집·추가·전송·뒤로 등 동작을 실제로 표현해야 한다. 임의 SVG 경로, 문자 기호, 의미 없는 장식 아이콘을 급조하지 않는다. 정식 SVG 에셋의 inline 사용은 허용하지만 출처·이름·선/채움·크기를 기록한다. 색·선 굵기·시각 크기를 통일하고 아이콘 버튼에는 접근 가능한 이름과 충분한 터치 영역을 둔다.

## 글자 크기 하한

사용자가 읽는 모든 UI 텍스트는 실제 계산된 크기 기준 **14 CSS px 이상**이다(RUI-09). 보조 설명·시간·배지·필터·버튼·placeholder·대화·오류에도 적용한다. 14px는 최대 크기가 아니라 하한이다. 본문·입력·주요 행동은 보통 16px에서 시작해 위계를 정한다. rem/em/clamp·미디어 쿼리·부모 상속·transform 축소로 하한을 우회하지 않는다. 공간이 부족하면 내용을 덜거나 배치를 바꾼다. 기존 토큰이나 레퍼런스가 12px여도 자동 채택하지 않는다. 스크린샷만으로 CSS px를 확정하지 않는다.

## CTA와 선택 컨트롤

먼저 각 조작을 `탐색 / 필터·선택 / 실행 CTA`로 분류한다(RUI-10). ‘전체·할 일·완료’는 필터이고 ‘편집·추가·저장·전송’은 행동이다. 같은 줄에 있어도 같은 모양을 반복해 역할을 섞지 않는다.

- 주요 CTA: 채움 등 명확한 버튼 표면과 실행을 예측할 수 있는 라벨을 둔다.
- 보조 행동: 윤곽선/적절한 표면 또는 의미 있는 아이콘+라벨로 조작임을 구분한다. 편집을 필터와 같은 회색 글자 하나로 두지 않는다.
- 필터·탭: 하나의 선택 그룹으로 묶고 선택 상태가 명확하게 보이도록 한다. 선택된 필터만 거대한 CTA처럼 강조하고 실제 행동은 숨기는 위계를 피한다.
- 텍스트 전용 버튼은 최소화한다. 본문 링크 등 명확한 맥락에 필요한 경우에만 이유를 남긴다. 모든 텍스트에 장식 아이콘을 붙이는 것은 해결이 아니다.

버튼의 윤곽선은 아래의 장식 구분선 금지와 다르다. hover 없이 기본 상태에서도 역할을 구별하고 focus/pressed/disabled를 확인한다.

## 보조 문구를 놓기 전에 삭제 검토

각 보조 문구에 `누가 지금 어떤 판단을 하는 데 필요한가 / 어느 행동과 연결되는가 / 삭제하면 잃는 정보는 무엇인가`를 묻는다(RUI-11). 답이 없으면 삭제한다. 제목 오른쪽이 비었다고 설명을 채우거나 `space-between`으로 관련 없는 두 문구를 양 끝에 놓지 않는다.

‘날짜와 시간도 함께’는 이번 실패의 예시이지 금칙어가 아니다. 자연어 입력 안내가 필요하면 입력 근처의 짧은 예시 또는 첫 사용 안내 한 곳에 둔다. 제목 옆 힌트·대화 첫 메시지·추천 칩·입력 아래 설명으로 같은 기능을 반복하지 않는다. 저장 범위처럼 사실상 필요한 정보는 숨기지 말고 필요한 시점과 가까운 위치에서 한 번 명확히 전달한다. 슬로건은 작업 정보가 아니다.

## 구획과 스크롤

영역을 나누기 위한 `<hr>`나 이를 흉내 낸 반복 border-top/bottom, 빈 요소, pseudo-element 수평선을 기본으로 넣지 않는다(RUI-14). 간격·정렬·묶음·짧은 제목·필요한 표면 차이로 구분한다. 줄을 없앤 자리를 카드·박스·큰 패딩으로 모두 대체하지 않는다. 입력·버튼·포커스·실제 표 데이터의 경계는 컨트롤/정보 역할로 판단하며 장식 구분선과 구별한다.

스크롤은 실제 내용이 가용 공간을 넘을 때만 생겨야 한다(RUI-13). ‘언젠가 길어질 수 있다’는 이유로 짧은 목록에 고정 높이와 overflow를 주지 않는다. 100dvh 프레임 안에 소개·달력·큰 채팅 패널을 쌓아 목록 공간을 줄였다면 먼저 불필요한 영역을 제거하거나 화면을 나눈다. overflow:hidden이나 스크롤바 숨김으로 콘텐츠 접근을 막아서는 안 된다.

빈 목록·1개·소수 항목·긴 목록을 각각 검사한다. 각 스크롤 영역의 clientHeight/scrollHeight, 잘리는 내용, 높이를 소비하는 형제를 실제 뷰포트에서 확인한다. 필요한 긴 대화/모달/문서 스크롤은 허용하되 원본 ORC-F16/G23의 적용·충돌도 남긴다. 키보드·큰 글자·짧은 높이에서 내용이 넘치면 읽고 실행할 수 있는 자연스러운 스크롤을 보존한다.

## 목록과 채팅은 화면 구조부터 결정

‘채팅으로도 만들기’는 목록 아래에 항상 큰 대화 패널을 붙이라는 뜻이 아니다(RUI-15). 목록에서 확인·완료하는 과제와 대화로 생성하는 과제가 서로 공간을 빼앗으면 `할 일 / 대화`처럼 별도 탭·뷰를 우선 검토한다. 짧은 일회성 입력이면 간결한 입력 영역이나 시트도 비교한다. 모든 앱에 탭을 무조건 추가하지 않고 핵심 과제와 전환 비용으로 선택한다.

채팅을 선택했다면 입력창만 닮게 만들지 않는다. 사용자 메시지 → 실제 처리 상태 → 결과·실패 → 수정/재시도의 흐름을 설계한다. 생성된 Todo는 목록과 연결하고 탭을 오가도 초안·선택·대화·목록 상태가 보존돼야 한다. 결과는 반복 메시지 대신 생성 대상과 다음 행동을 명확하게 보여준다. 로컬 동기 처리에 가짜 typing 지연이나 AI 응답을 연출하지 않는다.

최신 메시지 근처에서 전송하면 입력과 결과를 따라갈 수 있어야 한다. 과거 대화를 읽는 중에는 새 응답이 와도 강제로 아래로 끌지 않는다. 키보드 열림·닫힘, 긴 입력, 연속 생성, 실패 후 재전송, 화면 전환과 복귀를 실제로 확인한다. 애니메이션을 추가했다는 이유만으로 ‘스무스한 채팅’이라고 판정하지 않는다.

## Todo 요청에 대한 구조 예시

‘모바일 Todo, 채팅으로도 생성’ 요청에는 목록의 확인·완료를 기본 화면으로 두고 생성 경로를 짧게 제공한다. 지속적인 대화가 필요하면 별도 대화 탭에서 처리하고 생성 결과를 같은 목록 상태에 반영한다. 로고·슬로건·중복 힌트·장식 구분선을 추가하지 않고, 필터와 편집 CTA를 구분한다. 주간 달력도 날짜 탐색이 필요한지 검토한 뒤 선택한다. 이는 구조 판단 예시이며 모든 Todo에 복사할 고정 템플릿이 아니다.
