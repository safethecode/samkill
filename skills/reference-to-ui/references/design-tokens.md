# 디자인 토큰 계약

UI 디자인과 구현에서 필수로 사용한다. 레퍼런스 관찰은 증거이고 토큰은 우리 제품의 결정이다. 추정한 화면 픽셀을 확정 토큰으로 복사하지 않는다.

## 기존 시스템부터 확인

대상 프로젝트의 토큰 파일, 테마, 컴포넌트 변형, 아이콘 규칙, 사용처를 확인한다. 기존 이름과 표현 방식(CSS 변수, 테마 객체, 디자인 변수 등)을 따른다. 별도 라이브러리·새 프레임워크·기존 시스템 전체 교체를 요구하지 않는다. 사용자가 디자인 명세만 요청하면 논리적 이름·값·참조 관계만 제공하고 코드 변경은 하지 않는다.

읽는 글자는 기본14 CSS px 이상이다. [글자 크기 하한](ui-composition.md#글자-크기-하한)의 조건을 충족하는 짧은 보조정보만 최소12px 전용 토큰을 허용한다. 기존12px 토큰을 자동 재사용하거나 공통body/행동 토큰을 축소하지 않는다. 실제 사용처·예외 근거·좁은폭/확대 검증을 연결한다. 간격이나 아이콘 좌표와 글자 하한은 구별한다.

## 역할을 나누기

1. **기본 토큰:** 채택한 색상 값, 간격 단계, 글자 크기/굵기/줄높이/자간, 반경, 테두리, 그림자, 아이콘 크기/선 굵기, 필요한 모션 값. 실제 사용할 값만 만들고 불필요한 100단계 팔레트를 생성하지 않는다.
2. **의미 토큰:** surface/text/border/action/status, 영역 간격·컨트롤 높이·텍스트 역할 등 사용 목적. 같은 파랑이어도 링크와 주요 버튼은 앞으로 독립적으로 바뀔 역할이면 분리한다. 같은 역할은 화면마다 새 이름을 만들지 않는다.
3. **컴포넌트 토큰:** 버튼/입력/카드/아이콘의 변형·크기·상태별 별칭이 실제로 필요할 때 의미 토큰을 참조한다. 항상 3단계 별칭을 강제로 늘리지 않는다. 기존 시스템이 2단계면 그 구조 안에서 책임을 구분한다.

컴포넌트는 의미/컴포넌트 토큰을 사용한다. HEX·임의 px를 곳곳에 반복하거나 숫자에 이름만 붙인 `blue-button-1`, `padding-23-copy`를 완료로 취급하지 않는다. 이미 토큰에 연결된 유틸리티 클래스는 직접값이 아니다. 매직 넘버를 없애려다가 `0`, `100%`, `auto`, grid/flex 비율까지 무의미한 전역 토큰으로 만들지 않는다.

## 필수 전달 표

`토큰 이름 | 계층·역할 | 값 또는 참조 | 단위 | O/E/D-ID 또는 요구 근거 | measured/estimated/chosen/existing-token | 사용처 | 테마/상태 | 검증`.

관찰 추정은 별도 칸에 보존하고, 구현에 쓸 값을 골랐다면 `chosen`으로 표시한다. 값이 미정인 디자인 초안은 unknown을 허용한다. 실행되는 코드에는 해결되지 않은 참조를 남기지 않는다. 기본값만 만들고 컴포넌트 사용처를 비워 두면 구현 완료가 아니다.

## 버튼과 아이콘은 함께 정의

실행 CTA에 아이콘이 있으면 기본 순서는 label → icon이다. 공통 CTA 컴포넌트에서 오른쪽 배치와 gap을 일관되게 적용하고 왼쪽 배치는 방향/관례·명시 요구 등 이유 있는 변형으로만 둔다.

- 버튼의 `background / foreground / icon / border`를 한 묶음으로 정한다. 기본·hover·pressed·focus·disabled·loading 중 제품에서 필요한 상태를 정의한다. 미관찰 상태는 레퍼런스에서 가져온 것처럼 말하지 않고 제품 요구/기존 시스템에 따른 결정으로 쓴다.
- 텍스트는 font family/size/weight/line-height/letter-spacing, 컨트롤은 높이·사방 패딩·아이콘 gap·반경·테두리를 연결한다. 상태 변경 중 글자가 사라지거나 레이아웃이 바뀌는지도 확인한다.
- 아이콘의 크기/선 굵기/색은 토큰으로, outline/filled·cap/join·viewBox·패밀리는 컴포넌트/에셋 규칙으로 정한다. 문자열 토큰이 SVG나 에셋 규칙을 실제로 적용한다고 가정하지 않는다.
- 글자와 아이콘이 같은 색이면 foreground를 공유하거나 icon 별칭이 이를 참조하도록 한다. 아이콘이 `currentColor`를 쓰면 상위 색상 토큰과의 연결을 기록한다. 다른 색이면 역할 근거를 남긴다.
- 실제 필요한 테마·크기만 구현한다. 다크 모드 요구가 없는데 추가하지 않는다. 테마가 있으면 의미 이름은 유지하고 참조를 바꾼다. 배경만 바꾸고 글자/아이콘/테두리를 방치하지 않는다.

## 작은 예시 — 가상의 결정값이며 기본 디자인 프리셋이 아님

| 이름 | 값/참조 | 역할/출처 |
|---|---|---|
| color.brand.600 | #245EDB | 이 예시 제품이 고른 색, chosen |
| color.neutral.0 | #FFFFFF | chosen |
| action.primary.background | color.brand.600 | 주요 행동 배경 |
| action.primary.foreground | color.neutral.0 | 주요 행동 글자 |
| button.primary.icon | action.primary.foreground | 같은 색의 아이콘 |
| space.3 | 12 CSS-px | 이 예시의 chosen 간격 |
| control.padding.block | space.3 | 컨트롤 세로 여백 |
| button.medium.padding.block | control.padding.block | 실제 변형이 필요할 때의 별칭 |

이는 전체 버튼 명세가 아니다. 나머지 크기·상태·타이포그래피는 실제 요구에서 정한다. 예시 HEX/12px를 다른 프로젝트의 기본값으로 가져오지 않는다. 관찰된 24 image-px가 12 CSS-px라는 변환을 뜻하지 않는다.

## 화면 간 역할과 박스 관계

시각 주 제목은 HTML h1/h2 태그가 아니라 page/surface-title 역할로 연결한다. 날짜/시간 필드도 일반 입력과 같은 control 토큰 및 필요한 picker 변형을 사용한다. 목록/대화/폼의 같은 역할을 전수 대조하고, 부모 inset과 자식 margin/gap이 합쳐진 최종 거리까지 확인한다.

## 직접값과 검증

색·간격·글자·반경·그림자·아이콘 스타일은 토큰 사용을 기본으로 한다. 한 번만 쓰는 광학 정렬 보정, 콘텐츠 고유 비율, 외부 에셋의 내부 좌표처럼 토큰화가 부적절한 값은 `위치 | 값 | 이유 | 검증`으로 직접값 예외를 남긴다. 같은 예외가 반복되면 공통 역할로 승격할지 검토한다.

실제 코드에서는 정의 → 참조 → 사용처가 연결되는지, 미정의/순환 별칭이 없는지, 컴포넌트가 다른 직접값으로 덮어쓰는지 확인한다. 기존 린터/테마 검증 도구가 있으면 사용한다. 검색 결과에 px/HEX가 있다는 이유만으로 실패시키지 말고 토큰 원본·에셋·유틸리티 매핑·승인된 예외를 구분한다.

렌더에서는 배경과 글자/아이콘 대비, 사방 여백, 아이콘 정렬/스타일, 상태별 동작, 필요한 테마·크기를 검사한다. 정적인 토큰 검사와 시각 검증은 별도 결과다. 토큰을 바꾸면 의도한 사용처가 함께 바뀌는지도 관련 범위에서 확인한다. 문서·코드 검사만 했다면 실제 대비/렌더/테마 전환은 not-verified로 남긴다.

복합 입력의 focus 토큰은 현재 조작 대상의 표시 주체(입력 래퍼 또는 내부 컨트롤)에 연결한다. 같은 입력에 래퍼와 native outline/box-shadow를 중복 적용하지 않는다. 버튼 포커스·pressed·오류는 역할을 구별하고 키보드 및 고대비에서 표시가 유지되는지 실제 확인한다.

## 상태 전환과 모션

호버 표현의 필요성은 역할과 사용자 요구에 따라 정한다. 공통 버튼 hover가 사진/테마 영역에 불필요한 표면을 추가하는지 실제 진입·해제로 확인한다. 호버 표현을 제거한 요소도 클릭·키보드 focus-visible은 보존한다. 아래 전환 기준은 채택한 상태 변화에 적용한다.

호버 색·배경·테두리가 갑자기 바뀌는 조작에는 짧고 부드러운 전환을 기본으로 검토한다. 기존 제품의 모션을 우선하고, 없으면 상태 전환 120–180ms, 작은 표면의 등장·퇴장 180–240ms를 초기 결정값으로 시험한다. 이 범위는 레퍼런스 측정값이나 모든 제품의 고정 규칙이 아니다. duration/easing과 필요한 이동량을 역할 토큰으로 정해 버튼·입력·탭·대화의 같은 역할에 공유한다.

- 바뀌는 속성만 지정한다. `transition: all`로 크기·패딩·위치까지 우연히 움직이게 하지 않는다. 기본 상태에 전환을 정의해 hover 진입과 해제가 모두 자연스럽게 이어지게 한다.
- 색 변화만으로 충분하면 확대·튕김·떠오름을 더하지 않는다. 탭마다 화면 전체를 미끄러뜨리거나 새 메시지마다 목록 전체를 재등장시키지 않는다. 정지 레퍼런스로 모션을 관찰했다고 쓰지 않는다.
- 클릭 처리·저장·전송을 애니메이션 종료까지 늦추지 않는다. 빠른 재진입, 연속 클릭, 전환 중 취소에서도 움직임이 쌓이거나 내용·초점·스크롤 위치가 튀지 않게 한다.
- 터치에서는 hover가 없어도 pressed/선택 상태가 분명해야 한다. 키보드 포커스는 즉시 식별할 수 있게 하며 페이드 도중 사라지게 하지 않는다.
- `prefers-reduced-motion`에서는 불필요한 이동·확대·반복 효과를 제거하고 상태 정보와 조작 가능성을 보존한다. 전역 애니메이션 제거로 완료 콜백에 의존하는 기능을 깨뜨리지 않는다.

검증은 실제 hover 진입/해제·빠른 왕복, 눌림/해제, 키보드, 터치, 동작 줄이기 설정에서 수행한다. 정지 캡처나 CSS 선언만으로 부드러움을 통과시키지 않는다. 시간·곡선·사용처와 실제 관찰을 계약/리뷰에 연결하고, 미실행은 미검증으로 남긴다.

## 공통 화면 컨테이너의 패딩 소유권

목록·채팅처럼 같은 단계의 화면은 공통 컨테이너의 좌우 inset과 기본 상단 inset을 공유한다. 개별 화면에서 같은 역할의 패딩을 별도 값으로 덮어쓰지 않는다. 화면 바깥 여백, 섹션 내부 여백, 입력/버튼 내부 여백은 다른 역할이므로 모두 같은 숫자로 통일하지 않는다.

각 영역의 `공통 컨테이너 | 여백 소유 요소 | 토큰 | 자식 추가 inset | 뷰포트 기준 최종 거리`를 확인한다. 고정 composer는 공통 콘텐츠 폭·좌우 inset에 맞추고, 부모 안의 sticky/일반 흐름으로 바뀌면 부모 여백을 이중 적용하지 않는다. 이때 자식 padding-inline: 0은 최종 정렬을 유지하기 위한 선택일 수 있으므로 선언값만 비교해 결함으로 판단하지 않는다.

하단 탭·composer·safe area를 위한 가림 방지 공간은 기본 시각 패딩과 분리해 계산한다. 목록과 채팅의 padding-bottom을 무조건 같게 만들어 콘텐츠를 가리지 않는다. 반응형과 빈/긴 내용 상태에서도 제목·본문·고정 입력창의 의도한 좌우 기준선과 공통 상단 여백을 실제 렌더로 대조한다. 토큰 이름이 같아도 중첩 padding, margin, 폭, 위치 기준이 다르면 정렬이 다를 수 있다.

## 경계 상태와 레이아웃을 흔들지 않는 포커스

모션은 이동 효과뿐 아니라 border-color, 안쪽 경계의 box-shadow, 표면·글자색처럼 상태를 전달하는 표현을 포함한다. 필요한 속성에만 공통 duration/easing을 연결한다. 모든 요소에 그림자를 추가하거나 border-width·padding을 전환해 조작 영역을 흔들지 않는다.

입력의 **실제 DOM 초점은 input/textarea에 유지하고, 시각적 포커스 표시는 그 입력을 감싸며 보이는 필드 경계를 소유한 컨테이너에서 담당한다.** 내부 입력 박스나 폼 전체에 표시하지 않는다. 래퍼가 없다면 필드 단위 컨테이너를 구성한다. 컨테이너에 tabindex를 추가하거나 입력을 blur해 표시 위치를 옮기지 않는다.

일반 색상 모드의 입력 포커스는 컨테이너의 `box-shadow: inset 0 0 0 var(--focus-width) var(--focus-color)`로 구현한다. 두께·색은 기존 역할 토큰에 연결한다. border 추가·두께 변경·색 변경이나 외부 outline/ring을 입력 포커스의 대안으로 사용하지 않는다. 기본·오류 상태의 border는 유지할 수 있지만 초점 전후 두께와 내용 위치는 고정하고, inset shadow와 어긋난 이중선이 생기지 않게 조합한다. 장식 shadow가 있다면 상태 선언이 이를 우연히 덮어쓰지 않도록 구성한다.

대체 표시가 동작하는 해당 컴포넌트 안에서 내부 input/textarea의 기본 outline과 라이브러리 ring/box-shadow를 제거한다. 전역 outline 제거는 금지한다. 입력에 대응하는 초점 상태만 컨테이너에 전달한다. 입력만 있는 필드는 `:focus-within`을 사용할 수 있지만, 전송·지우기·보기 버튼이 함께 있으면 입력의 `:focus`/`:focus-visible`을 구별하는 선택자나 상태를 사용한다. 버튼으로 Tab 이동할 때 입력 컨테이너 강조를 해제하고 실제 버튼의 초점을 표시한다. 포인터 표시 정책은 아래 기준을 따르며 표시하는 경우의 위치와 방식은 동일하다.

이 규칙은 입력 필드의 시각적 초점에 적용한다. 버튼·링크 등 다른 조작의 포커스 방식까지 일괄 변경하지 않는다. border-box만으로 내부 폭까지 보존된다고 판단하지 않으며 외곽 크기·텍스트 위치·줄바꿈을 함께 확인한다.

키보드 초점 표시는 즉시 식별 가능하게 유지하고 추가 장식 전환만 부드럽게 한다. forced-colors에서는 box-shadow가 사라질 수 있으므로 시스템 색 outline 등으로 대체하며 중복 초점 표시를 만들지 않는다. 동작 줄이기에서도 초점·오류·선택 정보를 유지한다.

검증: 기본→hover→focus→오류+focus→blur에서 외곽 박스뿐 아니라 텍스트 시작점·내용 폭·줄바꿈·인접 요소 위치가 유지되는지 실제 대조한다. 키보드 이동, 고대비, 동작 줄이기에서 표시를 확인한다. 큰 blur나 반복 shadow 전환은 실제 부드러움도 확인하며 CSS 선언만으로 성능을 단정하지 않는다.

기술 근거: [MDN box-shadow](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/box-shadow), [forced-colors](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/forced-colors). 입력 필드에는 위 컨테이너 inset shadow 규칙을 적용하며 다른 컴포넌트로 범위를 확대하지 않는다.


포인터 초점 장식을 줄이도록 요청받으면 실제 focus를 blur하지 않고 키보드 표시를 보존한다. :focus-visible은 입력란에서 포인터 클릭에도 일치할 수 있으므로 실제 브라우저로 확인한다. 입력 방식 분기를 추가할 경우 Tab 전환·프로그램 초점 복귀·입력 caret·고대비 필드 경계와 선택 표시를 함께 검증한다.

## 반복 컨트롤의 상태별 치수 안정성

날짜·시간·옵션처럼 같은 역할의 컨트롤이 반복되고 일부에만 상태가 붙으면, 기본/선택/불가 상태의 외곽 크기·레이블 기준선·형제 행 높이를 비교한다. 상태용 문구·아이콘 추가가 한 항목을 키워 같은 grid/flex 행의 다른 조작까지 늘리지 않도록 **상태 정보를 놓을 자리와 치수 유지 방법**을 먼저 정한다. border-box나 개별 버튼 높이만 확인하지 말고 부모의 stretch와 형제의 최종 박스를 함께 본다.

선택 불가만 전달하면 충분한 상태는 disabled와 구별되는 표현으로 처리하고 접근성 이름에 필요한 사유를 보존한다. 설명이 판단에 필수라면 모든 컨트롤에 일관된 설명 공간을 확보하거나 그룹의 별도 설명 영역에 연결한다. 높이를 맞추려고 필수 설명을 삭제하거나 보이는 내용과 접근성 의미를 다르게 만들지 않는다.

상태 전환 전후와 여러 상태가 섞인 화면을 기본/좁은 폭·확대 글자에서 비교한다. 일반 본문, 사용자가 입력한 긴 내용, 명시적인 펼침 영역은 내용에 따라 늘어날 수 있다. 이 기준을 모든 요소의 고정 높이나 overflow 잘림 규칙으로 확장하지 않는다.

## 의미 묶음의 내부·외부 간격

제목과 보조 설명처럼 같은 정보를 설명하는 내부 간격과, 그 묶음에서 실제 목록/다음 작업으로 넘어가는 외부 간격을 구별한다. 둘을 같은 작은 값으로 압축해 소속과 위계를 흐리지 않는다. 특정 버튼을 첫 화면 안에 맞추기 위해 의미 경계의 여백부터 줄이지 말고 화면 전체의 밀도와 실제 스크롤 접근을 함께 판단한다. 고정 요소 때문에 끝까지 접근할 수 없는 가림은 반드시 수정하되, 정상 콘텐츠가 첫 화면 아래로 이어지는 것과 혼동하지 않는다. 모든 외부 간격을 같은 숫자로 강제하는 규칙은 아니다.
