요청: “테스트로 Todo List 만들어줘 html css 정도면 충분할 듯 지금은. 모바일에서 사용하기 쉬워야 해. 채팅으로도 할 수 있으면 좋겠네 투두 생성을”. 이번 독립 평가에서는 구현하지 않고 계약을 도출했다. reference-to-ui와 필수 구성/제품 본질/적용 형식/guardrails/토큰/mobile 참조, reference-review와 게이트/리뷰 기준/catalog v2, ux-copy와 한국어/문구 계약을 적용했다. writing-skills의 실제 적용 시나리오 평가이며 새 스킬을 이 실행에서 수정하지 않았다.

- O1: [mobile-initial.png](../fixtures/todo-feedback/mobile-initial.png)를 `view_image`로 직접 관찰. 이미지 파일은 390×844 image-px. 첫 화면과 목록 3행, 하단 생성 영역이 보인다.
- O2: [mobile-chat.png](../fixtures/todo-feedback/mobile-chat.png)를 같은 도구로 직접 관찰. 이미지 파일은 390×844 image-px. 9월 7일 목록 1행과 사용자 메시지/생성 결과가 함께 보인다.

## 실제로 도출한 최소 디자인 계약

**reviewer-derived 계약**이다. 사용자는 휴대폰에서 할 일을 빠르게 적고 다시 찾아 완료하려 한다고 가정한다. 핵심 과제는 제목·기한·완료 여부를 읽고 체크하는 것, 보조 생성 경로는 말로 입력하는 것이다. 성공은 생성된 내용과 날짜를 확인하고 같은 목록에서 완료할 수 있는 상태다. 날짜 파싱·저장·대화 엔진은 HTML/CSS만으로 구현됐다고 약속하지 않는다.

주 관찰 자료는 O1의 제목/시간/완료 조작이 정렬된 행 구조다. O2는 사용자 입력과 해석 결과의 연결 방식만 보조로 쓴다. 이는 좋은 레퍼런스로 전면 승인한 것이 아니다. 관찰에서 채택할 원리는 행의 빠른 훑어보기와 날짜 확인이며, 새 결정은 목록/대화의 뷰 분리다. 효과 가설은 목록의 가용 높이 확보, 비용은 대화 진입 1회와 복귀 상태 보존이다. 이 비용과 효과는 실제 전환 행동으로 검증한다.

모든 CSS 값은 **chosen**이며 이미지 측정값이 아니다. 화면 폭 390px는 좌우16px로 내용폭358px, 320px는 내용폭288px가 시작점이다. 390×844 및 320×740에서 같은 단일 열을 유지한다. 짧은 높이는 390×420과 320×420을 검사 목표로 정한다. 기본 문서 흐름으로 내용이 넘칠 때 페이지만 스크롤하며 목록에 고정 높이/overflow를 주지 않는다. 대화도 우선 자연 흐름으로 만들고, 키보드 때문에 composer가 가려지면 활성 입력을 볼 수 있게 조정한다. 실제 키보드가 열리는 동안 visual viewport·safe-area를 확인하기 전 `fixed`의 안정성을 약속하지 않는다. 긴 대화를 독립 feed로 바꿀 필요가 생기면 D5와 ORC-F16/G23 예외를 다시 검토한다.

**Do:** 목록 확인·완료를 첫 과제로, 제목과 기한은 함께, 기본 상태부터 행동 역할을 구분한다. **Avoid:** 임의 브랜드→일반 제목; 주간 달력 상시 점유→행별 기한과 필요 시 날짜 선택; 제목 옆 힌트·반복 예시→입력 가까이 한 예시; 반복 border→행 여백/정렬; 늘 열린 채팅→별도 뷰. **Intentional differences:** O1/O2의 동일 화면 목록+채팅, 로고, 달력, 반복 선을 채택하지 않는다. **Unknown:** 실제 저장 범위, 날짜 인식 문법/시간대, 대화 API, 모바일 브라우저 키보드, 접근성 트리, 최종 computed style. 이를 사용자용 문구에 구현 용어로 노출하지 않는다.

## 활성 규칙 검토와 남은 예외

catalog v2의 active 65개를 읽었다. 아래는 이 spec/fixture의 범위 매핑이며 실행 가능한 gate-contract/report가 아니다. 명세만 있다는 이유로 visual/interaction checks를 삭제하지 않았다.

- 적용 요소 없음: ORC-F01/F02/G10(사이드바), F09/G17(병렬 컬럼), G13/A09(카드 grid), A08(이미지 placeholder). A05는 정렬된 단일 열 과제이므로 억지 비대칭을 만들 대상이 없음. fixture 밖 다른 화면으로 미적용을 확대하지 않는다.
- 적용·후속 검사 유지: F03/F04/F06/F07/F10/F11/F12/F13/F14/F15, G01/G02/G03/G04/G05/G06/G07/G08/G09/G11/G12/G14/G15/G18/G19/G20/G21/G22/G24, A01/A03/A04/A06/A07, RUI-01–07. 대비·타입·치수·hover·시맨틱·토큰·실제 핵심 행동 전부를 정지 이미지로 통과 처리하지 않는다. RUI-06은 이 보고서에 생성 JS가 없지만 실제 앱 생성 코드의 검사 의무는 남는다. A06은 제목/기한을 숨기지 않는 밀도에 적용하며 사용자 Todo에 가격/판매자 정보를 임의 추가하지 않는다.
- 이번에 직접 드러난 범위: RUI-08/10/11/14/15는 V1/V3/V4/V6/V5. RUI-09/12/13은 V2/V7/V5의 코드 전달 사실과 미확인 실행을 함께 남긴다. 결과를 전부 fail 또는 pass로 일괄 채우지 않는다.
- EX-T1 / F05: 20개 이상 Todo도 제목·기한과 체크 중심의 모바일 행 목록으로 설계한다. 원본 `>20 → TABLE` 조건을 지우지 않고 이 범위 예외 제안으로 남긴다. G13은 카드 grid가 없어서 별도 미적용. 30개에서 읽기/조작/가로 넘침 검증 전 예외 PASS 아님.
- EX-T2 / F08/G16/A07: 핵심 완료 체크는 항상 보이고 제목이 연결된 라벨이다. hover에 숨기지 않는 이유는 모바일 터치 요구. 보조 수정은 명시적인 편집 모드. 실제 터치·키보드·접근성 검증은 아직 없음. 숨은 모든 동작을 허용하는 예외가 아니다.
- EX-T3 / F16/G23: 긴 내용은 페이지 스크롤로 처리한다. chat feed 허용 범위가 원본들 사이 다르므로 별도 feed를 무조건 예외화하지 않는다. 소수 항목의 프레임 압축은 허용하지 않으며 대화 길이/키보드 근거를 얻은 뒤 필요 범위만 예외 검토한다.
- EX-T4 / A02와 G01/RUI-14: 미세 gradient나 장식선을 강제하지 않고 입력의 실제 경계와 선택 표면으로 계층을 둔다. 흰 목록 전체에 texture를 넣지 않는 범위만 선언한다. 브랜드 없는 과제 화면이 이유이며 대조 판독 전 accepted PASS가 아니다.
- EX-T5 / A10: 로컬 동기 처리에는 skeleton/typing 지연을 연출하지 않는다. 빈 상태 삽화도 명시적 과제 역할이 없어 생략하는 제한 예외 제안이다. 실제 비동기 처리에는 실제 처리 표시, 오류에는 재시도/입력 보존이 필요하다. 모든 loading/error를 생략하는 예외가 아니다.
- 기존 PROJECT-CHAT/PERSISTENCE/MOBILE은 실행 결과를 재사용하지 않고 후속 검사 유지. PROJECT-FOOTER의 겹침 수정은 V5의 불필요한 스크롤 해결 증거가 아니며 PROJECT-INTRO의 공백 수정은 V4의 안내 필요성 해결 증거가 아니다. 새 PROJECT-NO-BRAND/ROLE-SEPARATION/SMALL-LIST/CHAT-RETURN은 각각 D1/D2/D3/D5의 제품 완료 조건으로 인계한다.

## 평가로 확인된 개선과 공백

개정 규칙을 실제로 적용하자 ‘토큰 있음/겹치지 않음/생성 결과 보임’에서 멈추지 않고 역할·불필요한 문구·공간 경쟁을 구체 항목으로 판독했다. 새 계약은 임의 로고를 만들지 않고 14px 하한, 별도 대화 뷰, 명확한 편집 버튼, 짧은 목록의 자연 흐름을 포함한다. 로고를 브랜드 예외로, 소수 목록 스크롤을 주 콘텐츠 예외로 사후 정당화하지 않았다.

남은 공백은 실제 모바일 사용 검증이다. 분리 뷰가 이 사용자에게 더 쉬운지는 가설이며 한 번의 독립 명세/fixture 평가로 여러 실행의 재현성이나 전체 스킬 배포 품질을 증명하지 못한다. 외부 좋은 레퍼런스와의 비교도 이번 범위 밖이다. Todo 구현, 렌더 생성, 클릭/키보드/스크롤 실행, lint/typecheck, 자동 디자인 게이트를 수행하지 않았다. 원본 Todo와 과거 판정은 수정하지 않았다.

## 후속 평가: 원본 레퍼런스 합성의 증명 가능성

초기 결과 작성 뒤 추가된 사용자 교정은 “결과가 레퍼런스와 닮지 않았고 비교할 품질이 아니며, 장점을 한 디자인으로 잘 결합해야 한다”는 것이다. 이후 [reference-synthesis.md](../../skills/reference-to-ui/references/reference-synthesis.md)와 RUI-16/17을 읽었다. 초기 실행 시 active65개였고 후속 catalog v2는 active67개다. 위 초기 평가를 삭제하거나 그때 67개를 읽었다고 바꾸지 않는다.

**이 계약만으로 원본 레퍼런스의 장점이 실제로 전달됐다고 입증할 수 없다.** O1/O2는 검토 대상 Todo 출력이지 그 출력이 참고한 원본이 아니다. 출력 내부에서 좋은 행 정렬을 관찰했다고 원본의 시각 문법을 보존한 증거로 삼을 수 없다. 사용자 피드백은 품질 실패의 전달 근거이며, 이 평가자는 원본 이미지가 없어 정확한 원본 대비 차이를 새로 판독하지 못했다.

RUI-16/17은 이 후속 요청에 적용된다. 검사 종류는 각각 `spec, visual` 그대로 유지한다. Q표로 대응 누락을 드러냈지만 원본 출처와 실제 비교가 비어 있어 게이트의 판정 근거는 **unknown**이며 자동 검사도 실행하지 않았다. 원본이 없다는 이유로 not-applicable 처리하지 않는다. 정확한 퇴보 부위를 확인하지 못한 상태에서 Q항목을 regressed로 새로 단정하지도 않는다.

현재 계약의 강점은 구성 결함을 피할 기준을 만든 점이다. 한계는 시각값이 chosen 중심이고 원본의 구체 비율·표면·간격 관계를 전달할 근거가 부족한 점이다. 따라서 이것을 완성된 레퍼런스 합성 계약이라고 납품하면 부족하다. 후속 작업에서는 실제 원본 목록 전체/행/조작 영역과 적절한 대화 레퍼런스를 확보하고 좋은 관계를 특정한 다음, Q1–4의 unknown을 관찰값으로 채우고 필요한 chosen 결정을 다시 검토해야 한다. 원본/구현의 표시 폭을 맞춘 전체·컴포넌트 비교, 콘텐츠 길이와 목표 CSS viewport를 기록한 결과, 실제 생성·복귀 실행이 있어야 retained/adapted-and-verified 여부를 판단할 수 있다.

이번 추가 평가는 원본 부재와 계약의 증명 범위를 확인한 것이다. 외부 검색·원본 비교·렌더·제품 수정을 수행하지 않았으며 사용자 피드백을 “취향 차이”로 해제하지 않았다.
