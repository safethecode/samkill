# 주문 관리 UI 구현 명세

산출물은 구현 명세다. 코드·브라우저·렌더 검증은 수행하지 않았다. `reference-unverified`: R1은 사용자 제공 관찰 기록이며 직접 본 이미지가 아니다. 이 기록으로 설계를 진행하고 추가 레퍼런스를 요구하지 않는다.

## 과제와 입력

운영자의 주문 비교 → 필터 → 여러 주문 선택 → 일괄 작업 → 실패 확인을 지원한다. 주 레퍼런스는 R1 하나이며 보조 화면은 불필요하다.

- O1: 사용자 제공 R1에서 너비 1440px, 주문 20행이 보임. 높이 미상.
- O2: 같은 기록에서 좁은 왼쪽 탐색, 상단 필터.
- O3: 같은 기록에서 금액 오른쪽 정렬.
- O4: 같은 기록에서 보이는 그림자 없음, 반경 약 4px(`estimated`).
- U1: 즉시 주문 관리 명세 제공, 과제와 무관한 장식 배제.
- U2: 기존 보라색 브랜드와 그라디언트 주요 CTA 유지.
- U3: 일괄 선택/작업, 긴 한국어 이름, 실패 상태 지원.

대상 너비는 1440px이다. 최초 구현 검사 높이 900px는 `chosen`이며 R1 높이가 아니다. 정확히 20행을 보장하거나 관찰된 너비만으로 행 높이를 역산하지 않는다. 코드베이스가 없어 아래 이름은 모두 예정 컴포넌트다. 브랜드 토큰은 재사용할 `existing-token` 대상이나 실제 색상·그라디언트 값은 unknown이다. 직접 측정한 값은 없다.

## 결정 계약

|---|---|---|---|---|---|
| D1 | O1, O2, U1 | 좁은 탐색 → 제목/행동 → 필터 → 선택 도구 → 주문 표. 탐색 160px, 본문 여백 24px chosen | OrdersPage | 1440px에서 표가 주 영역. 높이와 보이는 행 수 기록 | 현재 메뉴 표시와 키보드 접근 |
| D2 | O1, U3 | 기본 행 최소 40px, 글자 14px/줄높이 20px chosen. 긴 내용에 행 확장 허용 | OrdersTable | 긴 한국어가 겹치지 않음. 20행은 참고 밀도 | 선택 체크박스와 주문 상세 링크 분리 |

| D6 | O2, U3 | 검색·상태·기간 필터는 chosen. 현재 페이지 기준 선택 | Filters, BulkSelection | ‘현재 페이지 N건 선택’과 부분 선택 표시 | 아래 선택 정책 준수 |
| D7 | U3 | 긴 이름과 실패 사유를 별도 상태로 지원 | NameCell, FailureState | 긴 문구가 금액·행동을 덮지 않음 | 전문·사유 확인이 hover 없이 가능 |

표 열은 선택, 주문번호, 주문 일시, 주문자, 상태, 결제 금액, 상세 보기로 선택한다. R1에 이 열들이 실제 있었다는 주장은 하지 않는다. 주문자 열은 남는 공간을 우선 사용하고 2줄 이후 말줄임 시 항상 접근 가능한 ‘전체 이름 보기’를 제공한다. 공백 없는 한국어도 셀 안에서 줄바꿈한다. 날짜 표시 시작 형식은 `2026.09.06 14:05`이며 시간대는 서버 계약 확인 전 미확인이다.

검증 데이터는 **가상 데모**로 표시한다: `김하늘 / 128,000원`, `주식회사 서울생활문화연구소 온라인사업팀 김민서 / 12,345,678원 / 처리 실패`, 공백 없는 긴 조직명, 금액 누락, 0원, 20건 이상 행. 가상 데이터는 실제 주문으로 제시하지 않는다.

## 행동과 상태

1. 헤더 체크박스는 현재 페이지의 선택 가능한 행만 선택한다. 미선택/부분/전체 선택을 구분하며 선택 불가 행은 이유를 제공한다. 전체 검색 결과 선택은 포함하지 않는다.
2. 필터 적용·정렬·페이지 변경 시 선택을 해제하고 이를 알린다. 선택 수 0이면 주요 CTA를 비활성화하고 선택 안내를 제공한다.
3. 실행 중 선택·필터·페이지 변경과 중복 실행을 잠근다. 서버 근거 없는 진행률은 표시하지 않는다.
4. 전체 성공이면 선택 해제 후 갱신한다. 부분 실패이면 성공 건은 해제하고 실패 건 선택을 보존한다. ‘10건 중 8건 완료, 2건 실패’와 건별 사유를 보여주고 재시도 가능한 건만 재시도한다.
5. 응답 단절로 실행 결과가 불명확하면 ‘처리 결과를 확인하지 못했습니다’를 표시한다. 결과 확인·멱등성 계약 없이 자동 재실행하지 않는다.
6. 조회 중, 주문 없음, 조건에 맞는 결과 없음, 조회 실패, 개별 처리 실패를 구별한다. 조회 실패에는 다시 불러오기, 빈 검색에는 필터 초기화를 제공한다. 실패는 색상과 함께 텍스트로 표시한다.
7. 키보드 포커스를 모든 조작에 제공하고 상태 알림으로 결과를 전달한다. 패널을 닫으면 진입 버튼으로 돌아온다. 기본 세로 스크롤은 본문 하나를 사용한다. 실제 열 넘침에만 가로 스크롤을 허용한다. sticky 여부는 원본에서 추정하지 않는다.

실제 일괄 작업 종류, 권한, 지원 상태, API 오류·멱등성 계약은 unknown이며 연계 전 확정한다. 정지 화면으로 동작을 추정하지 않는다.

## Do / Avoid / Intentional differences / Unknown

**Do:** 좁은 탐색·상단 필터·정렬된 표·오른쪽 금액을 보존하고 긴 콘텐츠와 실패 상태에 맞춰 밀도를 조정한다.

**Avoid:** 주문 비교를 방해하는 대형 주문 카드 대신 표를 사용한다. 근거 없는 KPI·환영 hero·glow·다중 그림자 대신 실제 데이터와 선·간격을 쓴다. 행 hover scale 대신 배경/포커스를 사용한다. 원본 hover가 없다는 단정은 아니다.

**Intentional differences:** 브랜드 보라색과 그라디언트는 명시 요구로 보존한다. R1 색상이 미확인이므로 실제 색 차이는 확인되지 않았다. 긴 이름으로 행이 늘어날 수 있다. 선택/실패 정책은 과제에 따른 새 결정이다.

**Unknown:** 원본 이미지·높이·서체·정확한 간격/반경·상호작용·브랜드 토큰 값·API. 기존 시스템을 점검했다고 주장하지 않는다.

## 인계 및 검증

레이아웃/콘텐츠 → 타이포그래피/간격 → 표면/브랜드 → 동작 순서로 구현한다. 실제 파일이 생기면 예정 이름을 갱신하고 D-ID는 보존한다. V1은 D1–D4를 1440×900 chosen 뷰포트에서 검사하며 R1과 동일 밀도 판정을 유보한다. V2는 D5 브랜드/대비/포커스, V3은 D6 선택/필터/부분 실패, V4는 D7 긴 이름/누락/오류를 검사한다. **모두 미실행**이며 구현·시각 검증 완료를 뜻하지 않는다.

# 반례: 사진 중심 패션 상품 피드

단일 스크린샷의 전달 설명만 사용하며 `reference-unverified`로 진행한다. 추가 레퍼런스를 요구하지 않는다. F-O1은 사진 중심 피드, F-O2는 큰 둥근 상품 카드, F-U1은 브랜드 유지 요구다.

- F-D1 / F-O1: 예정 FashionFeed에 사진 → 상품명 → 가격 순서의 카드 그리드. 구현 시 사진 우선 위계와 긴 상품명을 검사한다.
- F-D2 / F-O2: 예정 ProductCard의 큰 반경 유지. 24px 시작값은 chosen이고 측정값이 아니다. 주요 피사체 크롭과 포커스 잘림을 검사한다.
- F-D3 / F-U1: 기존 브랜드 토큰 재사용, 값은 unknown. 이미지 로딩/실패·품절·키보드 진입 상태를 검사한다.

Do는 큰 사진·둥근 카드·브랜드 보존이다. Avoid는 사진을 가리는 근거 없는 glow/KPI이며 대안은 명확한 상품 정보와 일정한 간격이다. 큰 반경이나 카드 자체를 금지하지 않는다. 의도적 차이는 임시 반경과 접근성 처리이며 원본 대비 실제 차이는 미확인이다. 이미지 비율·열 수·뷰포트·토큰은 unknown이다. 주문용 4px·고밀도 표를 강제하지 않는다. 검증은 미실행이다.

# 관찰된 스킬 문제

- 필수 전달 계약은 실제 작성 가능했다. 다만 명세 전용 요청의 종료 분기가 없어 ‘실제 렌더 검증’을 요구하는 본문과 요청 범위를 구분해야 했다.
- application-format 예시가 이번 fixture의 1440px·20행·4px·보라색/gradient와 거의 같아, 이 결과만으로 다른 과제에 대한 일반화 성능을 판단하기 어렵다.
- 예시의 existing-token 표기가 브랜드 요구와 확인된 토큰 값을 혼동시킬 수 있다. 이번에는 재사용 대상과 미확인 실제 값을 분리했다.
- reference-unverified가 ‘직접 이미지 미확인’인지 ‘근거 전체 미확인’인지 정의가 짧다. 사용자 관찰의 출처를 인정하면서 직접 확인 여부를 별도 기록해야 했다.

수정 재검토: SKILL.md의 명세 전용 종료 규칙은 이 산출물을 `spec-only`이자 `reference-unverified`로 해석하게 하며 실제 렌더를 요구하지 않아 요청과 모순이 없다. application-format.md는 토큰 조회 전 unknown, 확인 후 existing-token으로 구분하므로 기존 명세의 ‘재사용 대상’ 표현보다 명확하다. 직접 이미지 미확인 상태의 의미도 추가되어 해당 모호함은 해소되었지만, 예시와 평가 fixture의 유사성 문제는 남는다.
